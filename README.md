# خط أنابيب تكامل وهندسة بيانات الطلاب (Student Data Integration & ETL Pipeline)

مشروع متكامل لهندسة وتكامل البيانات من مصادر متعددة وتجهيزها لأنظمة التحليل والذكاء الاصطناعي، مبني وفق أفضل الممارسات الهندسية ومبادئ البنية البرمجية النظيفة (Modular Architecture).

## 1. نظرة عامة على المشروع (Project Overview)

في بيئات العمل الإنتاجية، تكون البيانات التعليمية والأكاديمية موزعة بين عدة أنظمة مستقلة (ملفات مسطحة، واجهات برمجة تطبيقات سحابية، وقواعد بيانات علائقية). يهدف هذا المشروع إلى بناء خط أنابيب بيانات (ETL Pipeline) مؤتمت وقوي يقوم بسحب بيانات الطلاب من 3 مصادر مختلفة، وتوحيدها، وتنقيتها، ومعالجة القيم المفقودة والتكرارات، وتطبيق قواعد جودة صارمة لعزل البيانات غير الصالحة، وإنتاج مجموعة بيانات نهائية عالية الجودة جاهزة للتحليل الإحصائي ونماذج تعلم الآلة (Machine Learning Ready).

## 3. مصادر البيانات (Data Sources)

تم الاعتماد على 3 مصادر غير متجانسة:

1. **المصدر الأول – ملف CSV (`data/raw/students.csv`)**:
   - يحتوي على البيانات الديموغرافية الأساسية: `student_id`, `student_name`, `age`, `major`, `city`.
   - يحتوي على مشاكل جودة واقعية مقصودة لاختبار متانة الـ Pipeline (مسافات زائدة `" sanaa "`, حروف بأحجام مختلفة `"SANAA"`, أعمار غير منطقية `-4`, سجلات مكررة, وسجلات بدون معرف).

2. **المصدر الثاني – REST API (`mock_api.py` / `data/raw/students_api.json`)**:
   - يمثل واجهة خدمة أكاديمية توفر: `student_id`, `gpa`, `attendance`, `status`.
   - تدعم الفئة `APISource` الاتصال الشبكي الحي عبر مكتبة `requests`، وتتعامل باحترافية مع:
     - أخطاء انقطاع الاتصال (`ConnectionError`).
     - انتهاء مهلة الطلب (`Timeout`).
     - أكواد أخطاء HTTP (مثل `404`, `500`).
     - الاستجابات الفارغة وغير المتوافقة مع JSON (`Invalid JSON`).
     - التبديل التلقائي الذكي للبيانات المحلية البديلة عند تعذر الوصول للسيرفر (`Mock Fallback`).

3. **المصدر الثالث – قاعدة بيانات SQLite (`database/students.db`)**:
   - قاعدة بيانات علائقية تضم جدولي `courses` و `enrollments`.
   - تقوم الفئة `DatabaseSource` بتنفيذ استعلام `JOIN` تجميعي لحساب متوسط درجات الطالب في المقررات لضمان الحفاظ على مفتاح الربط الفردي `student_id`.

## 4. مراحل خط الأنابيب (ETL Pipeline Stages)

يمر تدفق البيانات بالمراحل الست التالية:

```
[CSV Source] ──┐
[REST API]   ──┼──> [1. Extract] ──> [2. Pre-Clean & Deduplicate] ──> [3. Integrate on student_id]
[SQLite DB]  ──┘                                                                │
                                                                                ▼
[Load: final_dataset.csv] <── [Valid] ── <── [5. Validate Rules] <── [4. Transform & Feature Eng.]
                                  │
[Load: rejected_records.csv] <── [Invalid]
```

1. **Extract (الاستخراج)**: استدعاء الفئات المشتقة من `BaseSource` لكل مصدر بشكل مستقل وموثق بالسجلات.
2. **Pre-Clean & Deduplicate (التنقية الأولية)**: إزالة الفراغات المتروكة في النصوص، توحيد حالة الأحرف، وإزالة التكرارات على مستوى المصدر الأولي مع الاحتفاظ بأول سجل صحيح.
3. **Integrate (الدمج وتكامل البيانات)**: دمج البيانات من المصادر الثلاثة عبر ربط علائقي (`Outer Merge`) باستخدام مفتاح `student_id`، مع توليد حقل `data_lineage` لتسجيل مصادر كل صف.
4. **Transform & Feature Engineering (التحويل وهندسة الميزات)**:
   - تحويل الأنواع النصية إلى أرقام عشرية وصحيحة مع تدقيق الأخطاء (`errors='coerce'`).
   - تعويض القيم المفقودة بالوسيط الحسابي (`Median`) لـ `gpa` و `attendance` وبالوسط الحسابي (`Mean`) لـ `score`.
   - اشتقاق عمود `performance_level`:
     - `GPA >= 3.5`: Excellent
     - `GPA >= 3.0`: Very Good
     - `GPA >= 2.5`: Good
     - `GPA >= 2.0`: Acceptable
     - `GPA < 2.0`: At Risk
   - اشتقاق عمود `attendance_status`:
     - `attendance >= 75%`: Good
     - `attendance < 75%`: Low
   - اشتقاق عمود `academic_standing`:
     - `score >= 60`: Passed
     - `score < 60`: Failed
5. **Quality Validation (التحقق والفرز)**: تطبيق القواعد المؤسسية الصارمة وتقسيم البيانات إلى بيانات مقبولة وأخرى مرفوضة.
6. **Load (التخزين)**: حفظ البيانات النهائية الصالحة في `data/processed/final_dataset.csv` وحفظ البيانات غير الصالحة في `data/rejected/rejected_records.csv`.

## 5. قواعد جودة البيانات وفرز المرفوضات (Data Quality Rules)

يطبق نظام الجودة القواعد السبع المنصوص عليها:
- **Rule 1**: معرف الطالب `student_id` لا يمكن أن يكون فارغًا (`NOT NULL`).
- **Rule 2**: معرف الطالب `student_id` يجب أن يكون فريدًا داخل مجموعة البيانات (`UNIQUE`).
- **Rule 3**: العمر يجب أن يقع ضمن النطاق المقبول: $16 \le \text{age} \le 80$.
- **Rule 4**: المعدل التراكمي يجب أن يقع ضمن النطاق الأكاديمي: $0.0 \le \text{GPA} \le 4.0$.
- **Rule 5**: نسبة الحضور يجب أن تتراوح بين $0\%$ و $100\%$.
- **Rule 6**: درجة المقرر يجب أن تتراوح بين $0$ و $100$.
- **Rule 7**: توافق المعرفات وصحة تكاملها عبر المصادر المختلفة.

أي سجل يخالف قاعدة أو أكثر يتم عزله فوراً وإرساله إلى ملف `data/rejected/rejected_records.csv` مع تسجيل سبب الرفض المفصل في عمود `error_reason` (مثل: `Invalid Age: -4 (Rule 3)` أو `Invalid GPA: 4.85 (Rule 4); Invalid Score: 150.0 (Rule 6)`).

## 6. متطلبات التميز المنفذة (Excellence Features)

1. **Pipeline Configuration (`config.yaml`)**:
   - إدارة مركزية لجميع المسارات، إعدادات مهلة الشبكة، حدود التحقق من البيانات، واستراتيجيات التعويض.
2. **Incremental Processing (المعالجة التزايدية)**:
   - فحص بصمة الملفات (`MD5 Hash`) لقاعدة البيانات وملف CSV وسجل الحالة في `logs/pipeline_state.json`؛ لتفادي إعادة الحساب المرهقة إن لم يطرأ تغيير على المصادر.
3. **Data Lineage (سلالة البيانات)**:
   - إضافة عمود `data_lineage` لكل سجل نهائي لمعرفة المصادر التي ساهمت في تكوينه (مثل `CSV + API + DATABASE`).
4. **Pipeline Metrics (مقاييس الأداء)**:
   - طباعة جدول ملخص تنفيذي بعد كل عملية معالجة يوضح أعداد السجلات وزمن التنفيذ بالثواني.
5. **Reusable Extensible Architecture (بنية قابلة لإعادة الاستخدام)**:
   - توفير فئة أساسية `BaseSource` تسمح بإضافة أي مصدر مستقبلي (مثل PostgreSQL، MongoDB، أو Parquet) بدون لمس منطق الـ Pipeline الرئيسي.

## 9. الإجابة عن الأسئلة النهائية للتكليف (Student Final Evaluation Q&A)

فيما يلي الإجابات الهندسية التفصيلية عن الأسئلة الاثني عشر الواردة في القسم 22 من وثيقة التكليف:

---

### س 1: لماذا نحتاج إلى Data Pipeline عند التعامل مع مصادر متعددة؟
**الجواب**:
1. **تعدد الصيغ والبروتوكولات (Heterogeneity)**: تختلف مصادر البيانات في طبيعتها؛ فبعضها ملفات مسطحة (CSV)، وبعضها استجابات شبكية غير متزامنة (JSON عبر REST API)، وبعضها جداول علائقية (SQL). الـ Data Pipeline يوحد طريقة استهلاك هذه المصادر عبر واجهة موحدة.
2. **ضمان جودة وتماسك البيانات (Data Consistency & Quality)**: المصادر المستقلة غالباً ما تحتوي على تضارب في الأنواع، ومسافات زائدة، واختلاف في تسمية الأعمدة، وتكرار في المعرفات. خط الأنابيب يضمن ألا تصل أي بيانات إلى وجهتها النهائية إلا بعد مطابقتها لقواعد العمل والمواصفات المعيارية.
3. **الأتمتة وقابلية التوسع (Automation & Scalability)**: يغني خط الأنابيب عن العمليات اليدوية المعرضة للخطأ البشري، مما يسمح بجدولة المعالجة بشكل متكرر والتعامل مع تدفقات بيانات متزايدة بكفاءة وموثوقية.

---

### س 2: ما الفرق بين Raw Data و Processed Data؟
**الجواب**:
- **البيانات الخام (Raw Data)**: هي البيانات كما تم جمعها من مصدرها الأصلي دون أي تعديل أو تنقية. قد تحتوي على قيم مفقودة (Missing Values)، سجلات مكررة (Duplicates)، أخطاء مطبعية ومسافات زائدة، أنواع بيانات غير ملائمة (نصوص بدلاً من أرقام)، أو قيم غير منطقية كأعمار سالبة أو درجات تتجاوز الحد الأقصى.
- **البيانات المعالجة (Processed Data)**: هي بيانات خضعت لعمليات التنقية والتحويل والتحقق؛ حيث تم توحيد بنيتها، وتصحيح أنواع حقولها، وتعويض المفقود منها أو عزله، واستبعاد القيم الشاذة والمخالفة، وإضافة ميزات مشتقة (Derived Features). وتكون هذه البيانات مهيأة وموثوقة للاستخدام المباشر في نماذج الذكاء الاصطناعي ولوحات المؤشرات (BI Dashboards).

---

### س 3: ما الفرق بين Extract و Transform و Load؟
**الجواب**:
- **Extract (الاستخراج)**: مرحلة الاتصال بمصادر البيانات المتعددة وقراءة البيانات الخام بأمان دون التأثير على أداء الأنظمة المصدرية، مع معالجة انقطاعات الاتصال وقيود الشبكة.
- **Transform (التحويل والتنقية)**: مرحلة تطبيق القواعد المنطقية والحسابية وهندسة البيانات؛ وتشمل تنظيف النصوص، تحويل الأنواع، دمج الجداول، تعويض القيم المفقودة، اشتقاق أعمدة جديدة، والتحقق من جودة البيانات.
- **Load (التحميل والتخزين)**: مرحلة كتابة وحفظ البيانات المعالجة والنهائية في المستودع الهدف (مثل Data Warehouse أو ملف CSV أو Data Lake) لتمكين المستخدمين النهائيين وتطبيقات التحليل من الوصول إليها بسرعة وكفاءة.

---

### س 4: ما المشاكل التي واجهتها أثناء دمج البيانات؟
**الجواب**:
1. **تفاوت أنواع مفتاح الربط (`student_id`)**: في بعض المصادر كان المعرف يُقرأ كنص (`"1001"`) وفي أخرى كعدد صحيح (`1001`)، وقد يحتوي على مسافات، مما تطلب معالجة نوعية موحدة وتحويل آمن للأرقام قبل محاولة الربط.
2. **تعدد السجلات لكل طالب في المصدر العلائقي (1-to-Many Relationship)**: يحتوي جدول التسجيلات `enrollments` على عدة مقررات لنفس الطالب؛ ودمجه مباشرة يؤدي لتكرار بيانات الطالب الديموغرافية، لذا تم تطبيق استعلام تجميعي (`GROUP BY e.student_id` مع `AVG(score)`) للحفاظ على علاقة 1:1.
3. **غياب بعض السجلات في مصادر معينة**: وجود طلاب في ملف الـ CSV ليس لديهم درجات في الـ Database أو العكس، مما تطلب استخدام الربط الخارجي (`Outer Join`) وتطبيق آلية تتبع سلالة البيانات (`Data Lineage`) لمعرفة اكتمال مساهمة كل مصدر.

---

### س 5: كيف تعاملت مع Missing Values؟
**الجواب**:
تم تبني استراتيجيات تعويض (Imputation) قائمة على طبيعة الحقل وتوزيعه الإحصائي وموثقة في إعدادات المشروع:
- **المعدل التراكمي (`gpa`) ونسبة الحضور (`attendance`)**: تم استخدام الوسيط الحسابي (`Median`)، لأن الوسيط مقاوم للقيم الشاذة والمتطرفة (Outliers) بخلاف المتوسط الحسابي، مما يحافظ على التوزيع الإحصائي الطبيعي للبيانات الأكاديمية.
- **درجة المقرر (`score`)**: تم استخدام المتوسط الحسابي (`Mean`) لتعويض الدرجات وفق المعايير الأكاديمية القياسية للتوزيع الطبيعي للدرجات.
- **الحقول النصية (مثل التخصص أو المدينة)**: تم التعويض بقيمة معيارية دلالية مثل `'Unknown'`.

---

### س 6: كيف تعاملت مع Duplicate Records؟
**الجواب**:
تم التعامل مع التكرار على مرحلتين:
1. **داخل المصدر نفسه (Source Deduplication)**: عبر فحص حقل المعرف الفريد `student_id` باستخدام `drop_duplicates(subset=['student_id'], keep='first')`، حيث يتم الاحتفاظ بالظهور الأول للسجل الصحيح واستبعاد التكرارات الناتجة عن أخطاء الإدخال المزدوج، مع تسجيل عدد التكرارات المستبعدة في تقرير الأداء.
2. **أثناء التحقق من الجودة (Rule 2)**: تم تضمين فحص التكرار كقاعدة صريحة لعزل أي سجل مكرر متبقٍ وتوجيهه إلى ملف السجلات المرفوضة مع توثيق سبب الرفض.

### س 7: كيف تعاملت مع Invalid Records؟
**الجواب**:
وفق المبدأ الهندسي القائل بأن "البيانات الخاطئة لا تُهمل ولا تُمرر"، تم تطبيق الآلية التالية:
1. بناء فئة تحقق مخصصة `DataQualityValidator` تفحص كل صف مقابل قواعد العمل السبع (مثل: عمر سالب، معدل أكبر من 4.0، حضور يتجاوز 100%).
2. فرز البيانات إلى تيارين منفصلين:
   - **تيار البيانات الصالحة (Valid Records)**: يكمل مساره إلى ملف `final_dataset.csv`.
   - **تيار البيانات المرفوضة (Rejected Records)**: يتم حفظه في `data/rejected/rejected_records.csv` مع إضافة حقل `error_reason` يحدد نصياً ورقمياً القاعدة التي تم انتهاكها والقيمة المخالفة.
3. يتيح ذلك لفرق إدارة الجودة والأنظمة المصدرية مراجعة الأخطاء وإصلاحها من المنبع دون تعطيل عمل الـ Pipeline.

### س 8: لماذا يجب فصل طبقة Extraction عن Transformation؟
**الجواب**:
1. **تطبيق مبدأ المسؤولية الواحدة (Single Responsibility Principle)**: فمهمة طبقة الاستخراج هي التعامل مع الاتصال الشبكي، والتوثيق، وصيغ التخزين الأولية، بينما مهمة التحويل هي تطبيق قواعد العمل وتنظيف البيانات.
2. **سهولة الصيانة والتطوير (Maintainability)**: إذا تغير عنوان الـ API أو تغيرت قاعدة البيانات من SQLite إلى PostgreSQL، يتم تعديل فئة الاستخراج فقط دون المساس بقواعد التنظيف والتحويل.
3. **إمكانية إعادة الاستخدام واختبار الوحدات (Testability)**: يتيح هذا الفصل اختبار منطق التحويل والتنظيف بمعزل تام عن الشبكة وقواعد البيانات الحقيقية عبر حقن بيانات وهمية (Mock Data).

### س 9: لماذا يعتبر Data Validation جزءًا أساسيًا من هندسة البيانات؟
**الجواب**:
1. **منع مبدأ "المدخلات السيئة تؤدي لمخرجات سيئة" (Garbage In, Garbage Out)**: تمرير درجات أو معدلات خاطئة لنماذج تعلم الآلة أو تقارير الأعمال يؤدي إلى قرارات إدارية كارثية ونماذج ذكاء اصطناعي غير مستقرة ومتحيزة.
2. **الكشف المبكر عن تدهور البيانات وتغير المخطط (Schema Drift & Data Drift)**: يضمن التحقق اكتشاف التغيرات غير المتوقعة في بنية بيانات المصادر قبل وصولها للمستودع النهائي.
3. **بناء الثقة في أصول البيانات (Data Reliability)**: يمنح مستهلكي البيانات (محللي البيانات وعلماء الذكاء الاصطناعي) يقيناً تاماً بأن البيانات المنشورة تلبي كافة المعايير النظامية والأكاديمية المعتمدة.

### س 10: كيف يمكن تطوير Pipeline ليعمل بشكل دوري وآلي؟
**الجواب**:
1. **أدوات إدارة وتنسيق التدفقات (Workflow Orchestration Engines)**: استخدام أدوات احترافية مثل **Apache Airflow**، أو **Prefect**، أو **Dagster** لتعريف الـ Pipeline كـ Directed Acyclic Graph (DAG)، مما يتيح الجدولة التلقائية، وإعادة المحاولة عند الفشل (Retries)، وإرسال تنبيهات بريدية أو عبر Slack.
2. **حاويات Docker وجدولة مهام السحابة (Containerization & Cloud Cron)**: حزم التطبيق داخل Docker Container وتشغيله عبر **Kubernetes CronJobs** أو خدمات Serverless مثل **AWS ECS Scheduled Tasks** أو **GCP Cloud Run Jobs**.
3. **البنية المعتمدة على الأحداث (Event-Driven Architecture)**: إطلاق تشغيل الـ Pipeline تلقائياً عند وصول ملف جديد إلى حوض تخزين سحابي (مثل S3 أو GCS Bucket) عبر Webhooks أو Cloud Functions.

### س 11: كيف يمكن جعل Pipeline يتعامل مع ملايين السجلات؟
**الجواب**:
1. **المعالجة الموزعة (Distributed Computing)**: الانتقال من المعالجة الأحادية إلى أطر العمل الموزعة مثل **Apache Spark** (عبر PySpark) أو **Dask** لمعالجة وتقسيم البيانات عبر عنقود من الأجهزة (Cluster).
2. **المعالجة على دفعات وتجزئة البيانات (Chunking / Batch Streaming)**: قراءة البيانات على دفعات باستخدام خاصية `chunksize` في Pandas أو DuckDB، مما يحافظ على استهلاك الذاكرة العشوائية (RAM) في حدود ثابتة.
3. **استخدام صيغ تخزين عمودية عالية الكفاءة**: استبدال ملفات CSV بصيغة **Parquet** أو **Delta Lake**، والتي توفر ضغطاً عالياً للبيانات وتدعم القراءة الجزئية وتخطي البيانات (Columnar Storage & Partition Pruning).
4. **دفع الحسابات لقواعد البيانات (ELT Approach)**: استخراج البيانات وتحميلها أولاً إلى مستودع سحابي عالي الأداء (مثل BigQuery أو Snowflake أو ClickHouse) وإجراء عمليات التحويل الضخمة داخله باستخدام محرك SQL الموزع.

### س 12: ما الفرق بين Batch Processing و Streaming Processing؟
**الجواب**:
| وجه المقارنة | المعالجة على دفعات (Batch Processing) | المعالجة الآنية / المتدفقة (Streaming Processing) |
| :--- | :--- | :--- |
| **طبيعة البيانات** | بيانات محددة ومجمعة مسبقاً (Bounded Dataset). | بيانات غير محدودة ومستمرة في التدفق (Unbounded Stream). |
| **زمن الاستجابة (Latency)** | يتراوح بين دقائق إلى ساعات أو أيام (High Latency). | في أجزاء من الثانية إلى ثوانٍ معدودة (Near Real-Time). |
| **آلية المعالجة** | جدولة زمنية دورية (مثل كل ساعة أو نهاية اليوم). | معالجة فورية لكل حدث بمجرد وقوعه (Event-by-Event / Micro-batches). |
| **التقنيات الشائعة** | Apache Spark, dbt, SQL Warehouses, Airflow. | Apache Kafka, Apache Flink, Spark Streaming. |
| **حالات الاستخدام** | التقارير الدورية، كشوف الرواتب، التدريب الدوري للنماذج. | كشف الاحتيال المالي، مراقبة أنظمة IoT، أنظمة التوصية الحية. |
